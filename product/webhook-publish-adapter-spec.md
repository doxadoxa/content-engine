# Webhook publish adapter — контракт

Спека, на которую ссылается §5 продуктового плана. Внешняя сторона видит именно
этот документ, поэтому он написан как контракт, а не как описание реализации:
всё, что здесь зафиксировано, приёмник вправе считать гарантией.

Версия контракта: **1**. Ломающие изменения — новая версия и оба адаптера рядом.

---

## 1. Транспорт

`POST` на `endpoint` канала, `Content-Type: application/json; charset=utf-8`.

| Заголовок | Значение |
|---|---|
| `Authorization` | `Bearer <secret>` |
| `X-Engine-Delivery` | UUID доставки |
| `X-Engine-Event` | `content.published` \| `content.updated` \| `content.deleted` \| `ping` |
| `X-Engine-Timestamp` | Unix-секунды на момент подписи |
| `X-Engine-Signature` | `sha256=<hex>` |
| `X-Engine-Contract` | Версия контракта, сейчас `1` |

### Подпись

```
signature = HMAC-SHA256(key: secret, message: "{timestamp}.{raw_body}")
```

Сравнение — только constant-time. Проверяется и timestamp: расхождение больше
**300 секунд** — отказ. Bearer без подписи недостаточно: заголовок утекает в
логи прокси целиком, подпись — нет.

### Коды ответа

| Код | Смысл для движка |
|---|---|
| 2xx | Принято. Тело может содержать `public_url`. |
| 409 | Уже видели этот `delivery_id`. Успех, не ошибка. |
| 401 / 403 | Подпись или токен неверны. **Не ретраится.** |
| 422 | Payload не прошёл валидацию приёмника. **Не ретраится.** |
| 408 / 425 / 429 / 5xx | Временно. Ретраится. |
| таймаут, DNS, отказ соединения | Временно. Ретраится. |

Различие принципиальное: 4xx (кроме 408/425/429) — это «вы прислали не то», и
повтор пришлёт то же самое.

## 2. Идемпотентность

`delivery_id` — UUID, уникальный на доставку. Приёмник **обязан** хранить
принятые `delivery_id` и на повтор отвечать 2xx или 409, не создавая вторую
публикацию.

Повтор — норма, а не сбой: доставка, ответ на которую потерялся, будет послана
снова с тем же `delivery_id`.

`replay` из дэшборда шлёт **сохранённый снапшот** под **новым** `delivery_id`.
Обратное — тот же id с сегодняшним контентом — не даёт приёмнику отличить
повтор от изменения.

---

## 3. Payload

Одна локаль на доставку. Локали связаны `locale_group_id` — это то, из чего
приёмник строит `hreflang`.

```jsonc
{
  "contract": 1,
  "event": "content.published",
  "delivery_id": "0198f4c2-...",
  "sent_at": "2026-08-06T10:00:00+00:00",
  "project": { "slug": "cleaning-point", "name": "Cleaning Point" },
  "content": {
    "id": "01kz...",                  // стабильный id юнита
    "locale_group_id": "01kz...",     // общий для всех локалей одного юнита
    "locale": "pt-PT",
    "slug": "como-limpar-janelas",
    "type": "how_to",
    "title": "Como limpar janelas",
    "summary": "…",                   // одна строка: meta description и llms.txt
    "markdown": "## …",
    "html": "<h2>…",
    "published_at": "2026-08-06T09:00:00+00:00",
    "images": [                       // фаза 8; до неё пустой массив
      { "role": "hero", "url": "https://…", "alt": "…", "anchor": null,
        "width": 1200, "height": 630 }
    ],
    "json_ld": { "@context": "https://schema.org", "@type": "HowTo", "…": "…" },
    "faq_json_ld": { "@type": "FAQPage", "…": "…" },
    "author": { "name": "…", "title": "…" },
    "internal_links": [ { "url": "…", "anchor": "…" } ]  // фаза 8; до неё пустой
  }
}
```

`content.deleted` несёт только `id`, `locale_group_id`, `locale`, `slug`.
`ping` не несёт `content` вовсе — это проверка связи и подписи при подключении.

### Ответ приёмника

```jsonc
{ "public_url": "https://cleaningpoint.pt/pt/como-limpar-janelas" }
```

`public_url` сохраняется в юните. Без него не работает матчинг с GSC в фазе 9,
поэтому приёмник, который его не вернул, считается подключённым не полностью —
это видно в дэшборде, но доставку не проваливает.

---

## 4. Ретраи

Лестница: **1м → 5м → 30м → 2ч → 12ч**. Пять попыток, потом `dead_letter`.

Каждая попытка — новая строка в логе доставки под тем же `delivery_id`:
приёмник обязан их дедуплицировать (см. §2).

`dead_letter` не удаляется и не ретраится сам по себе. Разбор — человеком, из
дэшборда, кнопкой replay.

---

## 5. Пакет `engine-receiver`

Composer-пакет для сайта-приёмника. Цель — подключение за 10 минут.

Даёт: маршрут, проверку подписи и timestamp, дедупликацию по `delivery_id`,
миграцию для принятого контента и минимальный рендер.

Проверка подписи и идемпотентность живут **в пакете**, а не в примере
интеграции: приёмник, который может их «забыть», рано или поздно забудет.

```php
// config/engine-receiver.php
return [
    'secret' => env('ENGINE_RECEIVER_SECRET'),
    'path' => 'engine/webhook',
    'tolerance' => 300,
    'public_url' => fn (array $content) => url("/{$content['locale']}/{$content['slug']}"),
];
```

---

## 6. Вне контракта

Батч-доставка, mTLS, ротация секрета через UI, pull API. Всё это — отдельные
версии контракта, а не флаги внутри этой.
