# Content Engine — продуктовый план

Мультитенантный сервис автоматизации контент-менеджмента: стратегия → контент-план → ежедневная генерация → публикация в блог и соцсети → петля обратной связи. Референс по UX — контент-план BabyLoveGrowth; по качеству и архитектуре движок должен его превосходить в четырёх местах: GEO-слой, петля обратной связи, дерево репурпоза в соцсети, полноценный webhook-контракт.

Стек: Laravel + Laragent (пайплайны агентов), Horizon + очереди, Postgres + pgvector, publish-адаптеры.

---

## 1. Позиционирование и стратегия

**Для кого сейчас:** собственные проекты (4 на старте: cryptoroute.io, Cleaning Point, + 2), с архитектурой «сервис с первого дня» — мультитенантность в ядре, но без SaaS-обвеса (биллинг, тимы, публичный онбординг). Обвес навешивается позже, если подтверждается внешний спрос.

**Дифференциация от рынка** (SEObot, Byword, Jasper, BabyLoveGrowth):

1. **GEO-native.** Каждый юнит контента строится под цитируемость в AI-ответах: FAQ/HowTo schema, quotable blocks, entity coverage, llms.txt-совместимость. Ниша «AI blog writer» переполнена; ниша «движок, делающий бренд цитируемым в ChatGPT/Perplexity/AI Overviews» — почти пуста.
2. **Feedback loop.** Движок смотрит на результат (GSC, индексация, AI-цитируемость) и корректирует план + обновляет деградирующие статьи. Дешёвые генераторы пишут в пустоту.
3. **Репурпоз-дерево.** Соцсети — не отдельная генерация, а производные от статьи-родителя с общими сущностями и ссылками. Единый голос + перекрёстное подтверждение сущностей работает на GEO.
4. **Brand Brief как живой артефакт.** Версионируемый документ вместо одноразового онбординга — решает главную боль генераторов («звучит не как мы») и даёт ручку управления без пересетапа.

**Главные риски:**

- *Google scaled content abuse.* Массовая генерация без оригинальных данных и экспертизы попадает под фильтр. Митигация: approve-режим по умолчанию (автопаблиш — привилегия, которую пайплайн зарабатывает на конкретном проекте), вставка оригинальных данных бизнеса (цены, кейсы, локальная специфика), разумная частота.
- *YMYL для cryptoroute.* Финансы/крипта — повышенные требования к точности и авторству. Фактчек-шаг и author schema с реальными именами там не опция, а обязательный этап пайплайна.
- *Себестоимость.* Токены на статью × 4 проекта × ежедневно. Метеринг с первого дня (см. §6), решения по моделям на шаг пайплайна — по данным, не по ощущениям.

## 2. Модель данных

```
Project (тенант)
 ├── BrandBrief          — версионируемый: позиционирование, ЦА, тон, запретные темы,
 │                          визуальный язык, примеры «нравится/не нравится», конкуренты.
 │                          Компилируется в промпты пайплайнов.
 ├── Channel              — publishing targets: webhook | wordpress | linkedin | x | telegram | pull_api
 ├── ContentPlan          — месячный, статус draft → approved
 ├── ContentItem          — контент-юнит (не «статья»!):
 │     ├── locales        — PT/EN/… как first-class сущности, связаны locale_group_id
 │     ├── derivatives    — дети-производные (соцпосты), наследуют сущности и ссылки родителя
 │     └── state machine  — idea → queued → generating → draft → approved → published → refreshing
 ├── Asset                — изображения (hero + inline с якорями размещения)
 ├── PipelineRun          — лог каждого запуска: шаги, токены, стоимость, латентность
 └── WebhookDelivery      — доставки: delivery_id, статус, код, latency, payload_snapshot, replay
```

Принципиальные решения:

- **Локали — first-class с первого дня.** Cleaning Point двуязычный, cryptoroute будет мультиязычным. Если локаль — поле у статьи, а не сущность, переписывание неизбежно.
- **Юнит ≠ статья.** Юнит — родитель дерева: локали × производные для каналов.
- **Brief версионируется.** Изменение тона — новая версия; старые публикации знают, на какой версии сделаны.

## 3. Три слоя продукта

### 3.1 Strategy-слой (Brand Brief)

Phase 0: Brief — структурированная форма, заполняется руками (для 4 своих проектов это вечер работы, и это же — эталонные примеры для будущего агента).

Phase 2: интерактивный онбординг-агент — чат, собирающий вводные (позиционирование, тон, брендинг, визуал на примерах) и компилирующий Brief. Делается в конце осознанно: к этому моменту есть 4 отработанных Brief'а как few-shot, агент соберётся сильно лучше, чем вслепую сейчас.

### 3.2 Планировщик

Keyword research (Ahrefs MCP как источник) → кластеризация по интентам → пул идей с difficulty/volume → типизация (how-to / explainer / product / comparison) → месячный календарь с деревьями репурпоза. Выход — draft-план на утверждение.

### 3.3 Исполнительный слой

Ежедневные воркеры по календарю. Каждый пайплайн — DAG агентов в Laragent, шаг = отдельный агент, состояние в БД, ретраи на шаг.

---

## 4. Пайплайны

| # | Пайплайн | Частота | Шаги |
|---|---|---|---|
| 1 | **Research** | еженедельно | Ahrefs → кластеризация интентов → пул идей (difficulty, volume) |
| 2 | **Planning** | ежемесячно | пул + Brief + существующий корпус → календарь с типами и репурпоз-деревьями → draft на аппрув |
| 3 | **Generation** | ежедневно | outline → драфт → фактчек → внутренняя перелинковка (эмбеддинги корпуса, pgvector) → schema + GEO-слой (FAQ, quotable blocks, entities) → изображения → draft/автопаблиш per-project |
| 4 | **Repurpose** | по родителю | статья → посты по каналам, форматные промпты из Brief, наследование сущностей и ссылок |
| 5 | **Publish** | событийно | доставка через адаптеры каналов (§5) |
| 6 | **Feedback** | Phase 2 | GSC API → индексация/показы/клики по юниту → сигналы в Planning + refresh-очередь + мониторинг AI-цитируемости |

## 5. Publish-адаптеры

Первый и основной — **универсальный webhook** (полная спека в `webhook-publish-adapter-spec.md`). Ключевое:

- События `content.published` / `content.updated` / `content.deleted` / `ping` (у BLG — только публикация; без updated не работает refresh).
- Bearer + HMAC-SHA256 подпись + timestamp против replay.
- Идемпотентность через `delivery_id`, ретраи с backoff (1м→5м→30м→2ч→12ч), dead-letter, replay из дэшборда.
- Payload: одна локаль на доставку, `locale_group_id` для hreflang, markdown + html, массив изображений с якорями, json_ld + faq_json_ld, author (E-E-A-T), internal_links.
- Приёмник возвращает `public_url` → сохраняется в юнит → матчинг с GSC в feedback loop.
- Composer-пакет `engine-receiver`: endpoint + миграция + рендер, подключение сайта за 10 минут.

Дальше по спросу: pull API (для SSG), WordPress, соцканалы как типы Channel (LinkedIn, X, Telegram — тот же механизм доставки, payload `social_post`). Зоопарк интеграций BLG (Wix, Duda, GoHighLevel…) — игнорировать.

## 6. Метеринг и юнит-экономика

Каждый `PipelineRun` пишет токены и стоимость по шагам. Дэшборд: себестоимость статьи по проекту, разбивка по шагам, тренд. Это нужно даже для внутреннего использования (главная метрика жизнеспособности), а при выходе в продажу — готовая основа биллинга.

---

## 7. Дэшборд

- **Календарь контента** (референс — скрин BLG): месяц, карточки со статусами (published / draft / generating / queued), тип контента, difficulty/volume, навигация по месяцам.
- **Карточка юнита:** превью, локали, дерево производных, история версий, аппрув/реджект с комментарием.
- **Каналы:** мастер подключения (URL → secret → test), лог доставок, replay, тумблер auto-publish per-channel.
- **Аппрувы:** очередь драфтов на сегодня — главный ежедневный экран оператора.
- **Метеринг:** стоимость по проектам/шагам.
- Phase 2: экран feedback — индексация, показы, деградация, AI-цитируемость, refresh-очередь.

---

## 8. Фазы

### Phase 0 — ядро (~3 недели)

Модель данных с мультитенантностью и локалями; Brief-форма; пайплайны Research + Planning + Generation; универсальный webhook-адаптер + пакет `engine-receiver`; дэшборд: календарь + аппрувы + лог доставок; метеринг.

**Критерий выхода:** 2 проекта публикуют ежедневно без участия оператора, кроме аппрува. Известна себестоимость статьи.

### Phase 1 — мультиканальность (~3 недели)

Репурпоз-дерево + 2 соцканала; пайплайн изображений полноценно; внутренняя перелинковка на pgvector; GEO-слой целиком; подключение оставшихся 2 проектов; WordPress-адаптер при необходимости.

**Критерий выхода:** 4 проекта, у каждого статья + производные в соцсети из одного юнита.

### Phase 2 — интеллект (~4 недели)

Feedback loop: GSC-интеграция, матчинг по public_url, сигналы в Planning; refresh-пайплайн (событие `content.updated`); мониторинг AI-цитируемости (проверка попадания в ответы ChatGPT/Perplexity по целевым запросам); онбординг-агент на базе накопленных Brief'ов; pull API.

**Критерий выхода:** план следующего месяца формируется с учётом фактических данных; минимум одна статья прошла цикл refresh по сигналу деградации.

### Gate «продавать или нет»

Решение — после Phase 1 на собственных метриках: себестоимость статьи, доля аппрувов без правок, динамика индексации/цитируемости. Если продавать: биллинг поверх метеринга, публичный онбординг через агента (Phase 2), white-label как у BLG — по спросу.

## 9. Технические решения (фиксация)

- Laravel-монолит, Laragent для агентных DAG, Horizon для очередей и расписаний.
- Postgres + pgvector (эмбеддинги корпуса для перелинковки и дедупликации тем).
- Модели: выбор per-шаг по данным метеринга (дорогая модель на outline/фактчек, дешёвая на рутину) — решается после Phase 0, не заранее.
- Ahrefs через MCP; GSC через официальный API (Phase 2).
- Изображения: генерация через API, hero 1200×630 + inline с якорями.
- Оркестрацию в Superpos не переносим на этом этапе (осознанное решение); архитектура шагов-агентов не должна этому мешать в будущем.

---

## 10. Вне скоупа

Биллинг и тарифы, тимы и роли, публичная регистрация, white-label, батч-доставка webhook, mTLS, rotate secret через UI, интеграции за пределами §5.
